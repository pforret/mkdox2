Update Zensical Docker image to latest version¶

Request¶

update Zensical Docker image to latest version

Analysis¶

The image pforret/mkdox-zensical (default for -D/--DOCKER in mkdox2.sh:49) is built from docker/Dockerfile, which starts FROM zensical/zensical:latest and adds third-party plugins (autolinks, awesome-pages, include-markdown, rss, markdown-include). Because the base is unpinned, "updating" mostly means rebuilding with a fresh pull of the base and pushing again; push_docker.sh builds without --pull, so a stale local zensical/zensical:latest can be reused.

Risks / open questions: - Should the base be pinned to an explicit Zensical version (e.g. zensical/zensical:<x.y.z>) for reproducible builds, instead of :latest? - push_docker.sh only pushes :latest; CLAUDE.md says the image shares VERSION.md (2.1.2), but no version tag is pushed. Consider also tagging pforret/mkdox-zensical:<VERSION>. - New Zensical releases may change CLI flags (serve --dev-addr) or plugin compatibility; verify serve and build still work. - Build is linux/amd64 only; arm64 (Apple Silicon) users run under emulation. - Pushing to Docker Hub is outward-facing and needs credentials.

Impacted files¶

  • docker/Dockerfile: pin base to zensical/zensical:0.0.74
  • docker/push_docker.sh: multi-arch docker buildx build --pull --push, tags :latest + :<zensical version>
  • mkdox2.sh: drop --platform linux/amd64 from the 3 docker run calls (lines 82, 235, 296)
  • CLAUDE.md: Docker image section (versioning/tagging is the Zensical version, multi-arch)

Plan¶

See the PRP below (pin 0.0.74, tag :latest + :0.0.74, multi-arch amd64+arm64).

Acceptance criteria¶

  • docker/Dockerfile starts FROM zensical/zensical:0.0.74
  • docker run --rm --entrypoint zensical pforret/mkdox-zensical --version prints 0.0.74
  • Docker Hub has pforret/mkdox-zensical:latest and :0.0.74, each a manifest list with linux/amd64 and linux/arm64
  • mkdox2.sh has no --platform flags; new, build and serve work natively on arm64 (no platform warning)
  • shellcheck mkdox2.sh docker/push_docker.sh and ./tests/run_tests.sh pass

PRP¶

Goal¶

pforret/mkdox-zensical is rebuilt on Zensical 0.0.74 (pinned, was 0.0.24 via an unpinned :latest), published as a multi-arch image (linux/amd64 + linux/arm64) under both :latest and :0.0.74, and mkdox2.sh no longer forces amd64 emulation, so mkdox new|build|serve run natively on Apple Silicon.

Why¶

  • The pushed image dates from 2026-02-28 and runs Zensical 0.0.24; 50 releases behind.
  • :latest base made builds non-reproducible and hid which Zensical a user runs; a version tag lets users pin with -D pforret/mkdox-zensical:0.0.74.
  • On arm64 Macs every docker run was emulated (slow serve/hot-reload, platform warnings).

Decisions taken¶

  • Base image reference → pin FROM zensical/zensical:0.0.74 (user)
  • Image tags pushed → :latest + :<zensical version> (e.g. :0.0.74), not the repo VERSION.md (user) (recorded: decisions/2026-11-01.tag-pforret-mkdox-zensical-with-latest.md)
  • Architectures → multi-arch now: linux/amd64 + linux/arm64, and remove --platform linux/amd64 from mkdox2.sh (user)
  • Source of the version tag in push_docker.sh → parsed from the FROM line of the Dockerfile, so the version lives in one place (default)
  • mkdox2.sh default -D image → stays pforret/mkdox-zensical (implicit :latest) (default)

Context the implementer MUST read¶

- file: docker/Dockerfile
  why: base image + pip plugin layer; ENTRYPOINT uses /sbin/tini from the base, keep it
- file: docker/push_docker.sh
  why: current build/push; build context is "." so it must be run from docker/ — make it cd to its own dir
- file: mkdox2.sh
  why: lines 82 (new), 235 (build), 296 (serve) pass --platform linux/amd64; line 49 is the -D default
- file: CLAUDE.md
  why: "Docker image" section claims the image shares VERSION.md — update to the new tagging
- url: https://github.com/zensical/zensical/releases
  section: releases 0.0.25 … 0.0.74
  critical: scan for renamed CLI flags (serve --dev-addr, build --config-file, new) and config changes before testing
- url: https://hub.docker.com/r/zensical/zensical/tags
  section: tag 0.0.74
  critical: base is published for amd64 and arm64 (verified with docker manifest inspect)
- url: https://docs.docker.com/build/building/multi-platform/
  section: "Build multi-platform images"
  critical: the local daemon uses the overlay store, not containerd, so a multi-platform build cannot --load; it must --push directly

Known gotchas & guardrails¶

  • Mirror the existing patterns named under Context; do not introduce new ones for this item
  • CRITICAL: multi-platform docker buildx build here can only --push, not --load; for local testing build one platform with --platform linux/arm64 --load (host is arm64) and test that before pushing
  • CRITICAL: pass --pull so the pinned base is fetched fresh, not taken from cache
  • The pip plugins (autolinks, awesome-pages, include-markdown, rss, markdown-include) must install on arm64 too; a failure there blocks the multi-arch push
  • PRESERVE: ENTRYPOINT/CMD, WORKDIR /docs, EXPOSE 8000; mkdox2.sh calls the image as … "$DOCKER" new|build|serve …
  • PRESERVE: the --user "$(id -u)":"$(id -g)" on new and all other docker run args; only remove --platform linux/amd64
  • Users who already have the old amd64 :latest cached keep it until docker pull pforret/mkdox-zensical; mention this in CHANGELOG.md
  • Pushing to Docker Hub is outward-facing: needs docker login as pforret; confirm with the user before running the push
  • Also update: CLAUDE.md Docker image section; CHANGELOG.md entry

Approach¶

Modify only existing files. docker/Dockerfile: pin the FROM tag. docker/push_docker.sh: cd to the script's directory, read the Zensical version from the Dockerfile's FROM line, then run one docker buildx build --pull --platform linux/amd64,linux/arm64 -t "$image:latest" -t "$image:$version" --push ., with set -euo pipefail. mkdox2.sh: drop --platform linux/amd64 from the three docker run calls. Order matters only here: test a single-arch local build before pushing, and push before relying on the new image in mkdox2.sh.

Validation loop (executable, in order)¶

# Level 1 — syntax/style
shellcheck mkdox2.sh docker/push_docker.sh
grep -c -- '--platform' mkdox2.sh                          # expect 0
head -1 docker/Dockerfile                                  # expect FROM zensical/zensical:0.0.74
# Level 2 — unit tests
./tests/run_tests.sh
# Level 3a — local single-arch image (before push)
(cd docker && docker buildx build --pull --platform linux/arm64 -t mkdox-zensical:test --load .)
docker run --rm --entrypoint zensical mkdox-zensical:test --version     # expect 0.0.74
tmp=$(mktemp -d) && cd "$tmp" && /Users/pforret/Code/mkdox/mkdox2/mkdox2.sh -D mkdox-zensical:test new demo && cd demo \
  && /Users/pforret/Code/mkdox/mkdox2/mkdox2.sh -D mkdox-zensical:test build && test -f site/index.html   # expect success, no platform warning
# serve (manual): ./mkdox2.sh -D mkdox-zensical:test serve, open the printed localhost URL, edit a page → hot-reload works
# Level 3b — push (after user confirms) and verify registry
bash docker/push_docker.sh
docker buildx imagetools inspect pforret/mkdox-zensical:0.0.74 | grep -E 'linux/(amd64|arm64)'   # expect both
docker buildx imagetools inspect pforret/mkdox-zensical:latest | grep -E 'linux/(amd64|arm64)'    # expect both
docker pull pforret/mkdox-zensical && docker run --rm --entrypoint zensical pforret/mkdox-zensical --version   # expect 0.0.74

  • Check the 0.0.74 base: Alpine, Python 3.14.4, /sbin/tini present, same ENTRYPOINT/CMD/WORKDIR
  • Pin FROM zensical/zensical:0.0.74 in docker/Dockerfile
  • Rewrite docker/push_docker.sh: cd to its own folder, read version from FROM, buildx --pull --platform linux/amd64,linux/arm64 --push, tags :latest + :<version>
  • Drop --platform linux/amd64 from the 3 docker run calls in mkdox2.sh
  • Level 1: shellcheck push_docker.sh clean; mkdox2.sh has only the pre-existing SC2001 style notes (lines 639/641)
  • Level 2: ./tests/run_tests.sh, 2/2 ok
  • Level 3a: local arm64 build → zensical 0.0.74, all 5 plugins installed; mkdox2 new (simple, with_blog), mkdox2 serve (page served, hot-reload picks up edit, no platform warning), mkdox2 build (simple, with_blog, legacy mkdocs.yml project) all OK

  • Level 3b: pushed (user confirmed); :latest and :0.0.74 both list linux/amd64 + linux/arm64 (same digest bb5cd59…); pulled image reports 0.0.74 on both arches; mkdox2 build with the default image OK

Confidence¶

9/10 that this can be implemented in one pass by an agent with only this file and the repo. Residual risk: a breaking change in Zensical 0.0.25–0.0.74 (CLI flags or a plugin failing on arm64) would need extra work.

Notes¶

  • Tested with mkdox2 from this repo (./mkdox2 → mkdox2.sh); the mkdox2 on PATH is a basher clone at the old commit and mkdox is the older MkDocs-based tool (user). (recorded: decisions/2026-11-01.command-hints-and-help-text-in.md)
  • Deviation: also fixed the post-new hints in mkdox2.sh (lines 187/191) to use $script_prefix serve (= mkdox2 serve) instead of hardcoded mkdox serve, and the option help text "for mkdox new/build" → "mkdox2".
  • mkdox2 new prompts for a template when -B is missing; use -B simple in non-interactive tests. docker run -it needs a TTY (script -q /dev/null … when testing from a non-terminal).
  • Deviation: the PRP assumed buildx --push works on the default builder; it doesn't ("Multi-platform build is not supported for the docker driver"). push_docker.sh now creates/reuses a docker-container builder mkdox-builder. The local single-arch --load test still uses the default builder.
  • docs/index.md (regenerated usage text) and the docs/PRPs/zensical-migration.md deletion in the working tree are the user's own, unrelated to this item.

Result¶

Verification¶

  • head -1 docker/Dockerfile → FROM zensical/zensical:0.0.74
  • docker run --rm --entrypoint zensical pforret/mkdox-zensical --version → 0.0.74 (no platform warning, local image arm64)
  • docker buildx imagetools inspect pforret/mkdox-zensical:0.0.74 and :latest → both list linux/amd64 + linux/arm64 (same digest bb5cd59…); amd64 variant also reports 0.0.74
  • grep -c -- '--platform' mkdox2.sh → 0
  • mkdox2 -B simple|with_blog new (test image) → rc 0, projects created; mkdox2 serve → page served on both templates, hot-reload picked up an edit, no platform warning; mkdox2 build → site/index.html for simple (5 pages), with_blog (11 pages) and a legacy mkdocs.yml-only project; mkdox2 build with the published default image → OK
  • shellcheck docker/push_docker.sh → clean; shellcheck -S warning mkdox2.sh → clean (only the pre-existing SC2001 style notes at lines 639/641 on the default level)
  • ./tests/run_tests.sh → 2/2 ok

Deviations from the spec¶

  • push_docker.sh creates/reuses a docker-container buildx builder mkdox-builder: the PRP assumed buildx --push works on the default builder, but the default docker driver refuses multi-platform builds even when pushing. (recorded: decisions/2026-11-01.use-a-dedicated-docker-container-buildx.md)
  • Added scope: the hints after mkdox2 new (mkdox2.sh lines 187/191) now use $script_prefix serve (= mkdox2 serve) instead of hardcoded mkdox serve, and the option help text says "mkdox2 new/build"; mkdox is the older MkDocs-based tool (user).
  • Shellcheck criterion: mkdox2.sh is not fully clean at the default level because of 2 pre-existing SC2001 style notes, untouched by this item. (recorded: decisions/2026-11-01.leave-pre-existing-sc2001-shellcheck-notes.md)

Discoveries¶

  • Zensical 0.0.33 moved the official image to Alpine; 0.0.68 needs Python ≥3.11 (0.0.74 ships 3.14.4). /sbin/tini, ENTRYPOINT/CMD and WORKDIR /docs are unchanged, and all 5 pip plugins install on arm64.
  • docker run --platform linux/amd64 <image> re-tags the local :latest to the amd64 variant; afterwards plain runs on arm64 warn and get emulated until docker pull --platform linux/arm64.
  • The mkdox2 on PATH is a basher clone (~/.basher/cellar/packages/pforret/mkdox2) at the old commit; it keeps forcing amd64 until it's updated.
  • mkdox2 new blocks on the template prompt without -B, and docker run -it needs a TTY, so the repo has no non-interactive smoke test for new/build/serve (tests only check usage output).
  • Unrelated changes in the working tree, not from this item: deleted docs/PRPs/zensical-migration.md (user), regenerated docs/index.md usage, and a rebuilt site/ folder.
