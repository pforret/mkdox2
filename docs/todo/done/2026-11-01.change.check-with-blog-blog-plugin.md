# Check with_blog template against Zensical blog plugin

## Request
check if the with_blog template uses the plugin https://zensical.org/docs/setup/blog/ correctly

## Analysis
A quick audit (template read + the `mkdox2 build` of a fresh with_blog project on Zensical 0.0.74
done for the Docker image update) gives this picture.

**Already correct:**
- `[project.plugins.blog]` with `blog_dir = "blog"` and the default layout `docs/blog/index.md` +
  `docs/blog/posts/*.md`, which matches the docs.
- `post_url_date_format = "yyyy/MM"` and `post_date_format = "medium"` are valid Material blog
  options. The build makes `/blog/2024/01/first-post/`, `/blog/archive/2024/` and
  `/blog/category/{content,fake}/`, and the blog index lists both posts.
- Posts have a `date:` (required), `categories:` and a `<!-- more -->` excerpt separator.
- `nav` is not set explicitly, so the docs need nothing more.
- The rss plugin makes `feed_rss_created.xml` with 2 items.

**Suspect or outdated:**
1. `mkdox2 blog` (mkdox2.sh, `blog)` action) overwrites `docs/blog/index.md` with a hand-made list
   of the 10 latest posts, linking `posts/<file>.md`. It also writes its own category and tag pages
   under `docs/blog/categories` and `docs/blog/tags`. With the native plugin, `blog/index.md` is
   just the entry point, and the plugin makes the post list, archive and category views itself. So
   this action duplicates the plugin and probably conflicts with it: double listings, and extra
   pages inside `blog_dir`. Confirmed by the user: `mkdox2 blog` predates Zensical's built-in
   blog, which didn't exist when it was written.
2. `docs/zensical/compatibility.md:47` says "`awesome-pages`, `blog`, `rss` are **not yet
   supported**", while line 17 says the blog is supported and the build shows it works. The page
   contradicts itself and is outdated for `blog`.
3. The posts have no `authors:` and there is no `docs/blog/.authors.yml`. The plugin's author
   support isn't shown at all. Optional, but a template is where people copy from.
4. Not covered: `draft: true` (shown in preview, left out of builds), the `date: {created,
   updated}` form, pagination, `pinned`, `links`, and restricting categories to a fixed list (which
   catches typos).
5. `mkdox2 post` writes `title:` + `date:` + `categories:` front matter into
   `docs/blog/posts/<date>-<slug>.md`. That's compatible, but it never adds `draft:` or `authors:`.
6. `awesome-pages` is enabled next to the blog. compatibility.md says Zensical doesn't support it
   (Zensical's own nav replacement is `awesome-nav`). It needs checking whether it does anything or
   is silently ignored.

**Confirmed by experiment during planning** (fresh with_blog project, Zensical 0.0.74):
- `mkdox2 blog` + build → the hand-made list in `blog/index.md` is shown above the plugin's own
  list, with mangled excerpts ("…poet. more Society…"), and `/blog/categories/{content,fake}/`
  is created next to the plugin's `/blog/category/{content,fake}/`.
- Building with and without `[project.plugins.awesome-pages]` gives the same nav (no `.pages` files
  in any template); it does nothing.
- RSS is generated by Zensical itself ("Zensical RSS"), but every `<link>` is `d_blog.test/…`
  without a scheme, because `mkdox2 new` fills `{SITE_URL}` with the bare `<name>.test`.

All open questions were settled during planning (see PRP, Decisions taken).

## PRP

### Goal
The with_blog template uses only Zensical's built-in blog: `mkdox2 blog` (a stand-in written
before Zensical had a blog) is removed, the template shows authors and a draft post, the dead
`awesome-pages` entry is gone from all templates, and new projects get a `site_url` with a scheme so
RSS, sitemap and canonical links are valid.

### Why
- `mkdox2 blog` now produces duplicate listings and a second set of category pages next to the plugin's.
- The template is what users copy; it should show the plugin's real features (authors, drafts) and nothing dead.
- RSS feeds of every new project currently contain broken links.

### Decisions taken
- `mkdox2 blog` → removed entirely, no message or mkdocs.yml-only mode (user) (recorded: decisions/2026-11-01.remove-the-mkdox2-blog-action-zensical.md)
- Template scope → `.authors.yml` + `authors:` on posts + one `draft: true` example; no pagination/pinned/links showcase (user) (recorded: decisions/2026-11-01.with-blog-template-shows-authors-and.md)
- `awesome-pages` → removed from all 6 templates' zensical.toml (user) (recorded: decisions/2026-11-01.remove-the-awesome-pages-plugin-entry.md); the pip package in docker/Dockerfile stays until a later image update (default)
- `site_url` → `https://<name>.test/` for every template, fixed in mkdox2.sh (user) (recorded: decisions/2026-11-01.mkdox2-new-fills-site-url-with.md)
- Author id in `.authors.yml` → `{USERNAME}` placeholder (filled by `whoami`), name = `{USERNAME}` too (default)
- `mkdox2 post` → unchanged (no `authors:`/`draft:` added), since a project may lack `.authors.yml` and an unknown author breaks the build (default)
- `find_md_*` helpers → remove only those with no caller left after the `blog)` removal (default)

### Known gotchas & guardrails
- Mirror the existing patterns named under Context; do not introduce new ones for this item
- CRITICAL: the template copier in `new)` runs placeholder substitution only on `.md/.pre/.post/.yml/.toml` files, and uses `find . -type f`, so `docs/blog/.authors.yml` is copied and gets `{USERNAME}` replaced. Verify it lands in the new project.
- CRITICAL: `{USERNAME}` = `whoami`, which can contain characters YAML dislikes (e.g. a dot is fine, but a space isn't). Keep the YAML key plain; quote the `name:` value.
- PRESERVE: the `post)` action and its blog_dir detection; `find_md_date` (still used by `toc`)
- PRESERVE: `{SITE_URL}` stays a placeholder in the templates; only the value mkdox2.sh puts in changes. Keep a trailing slash (`https://<name>.test/`).
- The README.md/docs/index.md usage block ("use mkdox2 blog …") is regenerated from the script's `#TIP` lines; don't hand-edit it, it disappears with the TIPs. `docs/index.md` already has uncommitted changes from the user; leave them.
- `docs/blog/index.md` in the template stays as the plain entry point (`# News`); the plugin appends the list.
- Also update: CHANGELOG.md Unreleased (`mkdox2 blog` removed: the blog plugin generates index, archive and categories; site_url now has https://)

### Discoveries
- Removing `find_md_raw_title` makes `shellcheck mkdox2.sh` clean at the default level, so the planned "CI workflows never run on main" item no longer has to choose between fixing SC2001 and lowering the severity.
- Zensical ignores plugins not on its supported list, and RSS is native ("Zensical RSS"). Of the 5 pip packages in docker/Dockerfile, `mkdocs-autolinks-plugin` and `mkdocs-awesome-pages-plugin` are unsupported, and `include-markdown`/`rss` are native, so installing them does nothing. `markdown-include` is a Markdown extension; still to check (covered by the planned "Add Zensical plugins to the templates" item).
- docs/zensical/compatibility.md still claims `git-revision-date-localized`, `git-authors`, `git-committers` are "Native built-in", but Zensical's plugin page lists them as **Planned** (old rows, not touched here).
- `.authors.yml` avatar `https://github.com/{USERNAME}.png` is only right when the local `whoami` equals the GitHub username.
- `mkdox2 build -I` (mkdox2.sh ~216-220) calls `mkdox -R -Q toc` / `mkdox -R -T toc`, which is the old MkDocs-based tool, not mkdox2. Bug.
- `mkdox2 serve` writes draft posts into `site/`, but `mkdox2 build` empties `site/` first (checked with a leftover draft page), so drafts don't leak into a build.
