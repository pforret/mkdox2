# Update Zensical Docker image to latest version

## Request
update Zensical Docker image to latest version

## Analysis
The image `pforret/mkdox-zensical` (default for `-D/--DOCKER` in `mkdox2.sh:49`) is built from
`docker/Dockerfile`, which starts `FROM zensical/zensical:latest` and adds third-party plugins
(autolinks, awesome-pages, include-markdown, rss, markdown-include). Because the base is unpinned,
"updating" mostly means rebuilding with a fresh pull of the base and pushing again;
`push_docker.sh` builds without `--pull`, so a stale local `zensical/zensical:latest` can be reused.

Risks / open questions:
- Should the base be pinned to an explicit Zensical version (e.g. `zensical/zensical:<x.y.z>`)
  for reproducible builds, instead of `:latest`?
- `push_docker.sh` only pushes `:latest`; CLAUDE.md says the image shares `VERSION.md` (2.1.2),
  but no version tag is pushed. Consider also tagging `pforret/mkdox-zensical:<VERSION>`.
- New Zensical releases may change CLI flags (`serve --dev-addr`) or plugin compatibility;
  verify `serve` and `build` still work.
- Build is `linux/amd64` only; arm64 (Apple Silicon) users run under emulation.
- Pushing to Docker Hub is outward-facing and needs credentials.

## Impacted files
- `docker/Dockerfile`: pin base to `zensical/zensical:0.0.74`
- `docker/push_docker.sh`: multi-arch `docker buildx build --pull --push`, tags `:latest` + `:<zensical version>`
- `mkdox2.sh`: drop `--platform linux/amd64` from the 3 `docker run` calls (lines 82, 235, 296)
- `CLAUDE.md`: Docker image section (versioning/tagging is the Zensical version, multi-arch)

## Plan
See the PRP below (pin 0.0.74, tag `:latest` + `:0.0.74`, multi-arch amd64+arm64).

## Acceptance criteria
- `docker/Dockerfile` starts `FROM zensical/zensical:0.0.74`
- `docker run --rm --entrypoint zensical pforret/mkdox-zensical --version` prints `0.0.74`
- Docker Hub has `pforret/mkdox-zensical:latest` and `:0.0.74`, each a manifest list with `linux/amd64` and `linux/arm64`
- `mkdox2.sh` has no `--platform` flags; `new`, `build` and `serve` work natively on arm64 (no platform warning)
- `shellcheck mkdox2.sh docker/push_docker.sh` and `./tests/run_tests.sh` pass

## PRP

### Goal
`pforret/mkdox-zensical` is rebuilt on Zensical 0.0.74 (pinned, was 0.0.24 via an unpinned `:latest`),
published as a multi-arch image (linux/amd64 + linux/arm64) under both `:latest` and `:0.0.74`, and
`mkdox2.sh` no longer forces amd64 emulation, so `mkdox new|build|serve` run natively on Apple Silicon.

### Why
- The pushed image dates from 2026-02-28 and runs Zensical 0.0.24; 50 releases behind.
- `:latest` base made builds non-reproducible and hid which Zensical a user runs; a version tag lets users pin with `-D pforret/mkdox-zensical:0.0.74`.
- On arm64 Macs every `docker run` was emulated (slow serve/hot-reload, platform warnings).

### Decisions taken
- Base image reference → pin `FROM zensical/zensical:0.0.74` (user)
- Image tags pushed → `:latest` + `:<zensical version>` (e.g. `:0.0.74`), not the repo VERSION.md (user) (recorded: decisions/2026-11-01.tag-pforret-mkdox-zensical-with-latest.md)
- Architectures → multi-arch now: linux/amd64 + linux/arm64, and remove `--platform linux/amd64` from mkdox2.sh (user)
- Source of the version tag in push_docker.sh → parsed from the `FROM` line of the Dockerfile, so the version lives in one place (default)
- `mkdox2.sh` default `-D` image → stays `pforret/mkdox-zensical` (implicit `:latest`) (default)

### Known gotchas & guardrails
- Mirror the existing patterns named under Context; do not introduce new ones for this item
- CRITICAL: multi-platform `docker buildx build` here can only `--push`, not `--load`; for local testing build one platform with `--platform linux/arm64 --load` (host is arm64) and test that before pushing
- CRITICAL: pass `--pull` so the pinned base is fetched fresh, not taken from cache
- The pip plugins (autolinks, awesome-pages, include-markdown, rss, markdown-include) must install on arm64 too; a failure there blocks the multi-arch push
- PRESERVE: ENTRYPOINT/CMD, `WORKDIR /docs`, `EXPOSE 8000`; mkdox2.sh calls the image as `… "$DOCKER" new|build|serve …`
- PRESERVE: the `--user "$(id -u)":"$(id -g)"` on `new` and all other `docker run` args; only remove `--platform linux/amd64`
- Users who already have the old amd64 `:latest` cached keep it until `docker pull pforret/mkdox-zensical`; mention this in CHANGELOG.md
- Pushing to Docker Hub is outward-facing: needs `docker login` as pforret; confirm with the user before running the push
- Also update: CLAUDE.md Docker image section; CHANGELOG.md entry

### Approach
Modify only existing files. `docker/Dockerfile`: pin the `FROM` tag. `docker/push_docker.sh`: `cd` to the
script's directory, read the Zensical version from the Dockerfile's `FROM` line, then run one
`docker buildx build --pull --platform linux/amd64,linux/arm64 -t "$image:latest" -t "$image:$version" --push .`,
with set -euo pipefail. `mkdox2.sh`: drop `--platform linux/amd64` from the three `docker run`
calls. Order matters only here: test a single-arch local build before pushing, and push before
relying on the new image in mkdox2.sh.

### Deviations from the spec
- `push_docker.sh` creates/reuses a `docker-container` buildx builder `mkdox-builder`: the PRP assumed `buildx --push` works on the default builder, but the default docker driver refuses multi-platform builds even when pushing. (recorded: decisions/2026-11-01.use-a-dedicated-docker-container-buildx.md)
- Added scope: the hints after `mkdox2 new` (mkdox2.sh lines 187/191) now use `$script_prefix serve` (= `mkdox2 serve`) instead of hardcoded `mkdox serve`, and the option help text says "mkdox2 new/build"; `mkdox` is the older MkDocs-based tool (user).
- Shellcheck criterion: `mkdox2.sh` is not fully clean at the default level because of 2 pre-existing SC2001 style notes, untouched by this item. (recorded: decisions/2026-11-01.leave-pre-existing-sc2001-shellcheck-notes.md)

### Discoveries
- Zensical 0.0.33 moved the official image to Alpine; 0.0.68 needs Python ≥3.11 (0.0.74 ships 3.14.4). `/sbin/tini`, ENTRYPOINT/CMD and `WORKDIR /docs` are unchanged, and all 5 pip plugins install on arm64.
- `docker run --platform linux/amd64 <image>` re-tags the local `:latest` to the amd64 variant; afterwards plain runs on arm64 warn and get emulated until `docker pull --platform linux/arm64`.
- The `mkdox2` on PATH is a basher clone (`~/.basher/cellar/packages/pforret/mkdox2`) at the old commit; it keeps forcing amd64 until it's updated.
- `mkdox2 new` blocks on the template prompt without `-B`, and `docker run -it` needs a TTY, so the repo has no non-interactive smoke test for new/build/serve (tests only check usage output).
- Unrelated changes in the working tree, not from this item: deleted `docs/PRPs/zensical-migration.md` (user), regenerated `docs/index.md` usage, and a rebuilt `site/` folder.
